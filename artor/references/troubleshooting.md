# Troubleshooting

Symptom → cause → fix. Error strings below are the CLI's exact output; match against them, then apply
the fix. When the message is relayed from the server (e.g. `pull failed (HTTP …)`), read the relayed
text rather than expecting fixed CLI wording.

| Symptom (what you see) | Cause | Fix |
| --- | --- | --- |
| `command not found: artor` (or similar) | CLI not installed | Install it — the CLI publishes to npm as **`artor-cli`** (command stays `artor`): `npm install -g artor-cli` (or `pnpm add -g artor-cli`). Re-run `artor --version`. |
| ``This CLI is too old for the Artor server. Run `artor update`.`` (HTTP 426) | Server's minimum-CLI floor was bumped, and the CLI's automatic self-heal (0.16.0+: update + re-run the command once) wasn't possible here (CI, `npx`/project-local install, auto-update off, or the update failed) | `artor update`, then retry the command. |
| `This server does not support the current publish protocol. The server is older than this CLI; ask your Artor operator to update it.` | The **server** predates the streaming publish protocol (the reverse of the 426 case) | Nothing on the CLI side fixes this — the self-hosted Artor server needs updating. Tell the user to contact their operator. |
| ``boot smoke test failed: the bundle crashes on `node <entry>` before binding its port: …`` (ends: ``Fix the build, or re-run with `--no-smoke` if your app legitimately needs runtime env/services to boot.``) | The built bundle crashes on startup (e.g. missing dependency, bad import) | Read the crash output and **fix the build**. Only re-run with `--no-smoke` if the app **legitimately** needs live secrets/services to boot — never as a reflex to bypass a genuine crash. |
| `couldn't detect a framework, a build script, or an index.html. Pass --dir <build-output>, or --node --entry <server.js> for a server.` | Running `publish` where there's no detectable app — usually a **monorepo/workspace root** | `cd` into the specific app's folder (the one whose `package.json` has the `build` script + framework dep) and publish there. Or pass `--dir`/`--node --entry` if the output/entry is non-standard. |
| ``no `build` script in package.json. Pass --dir <build-output> instead.`` | Same as above — cwd has a `package.json` but no `build` script | `cd` into the real app folder, or pass `--dir <build-output>`. |
| `found .html files but no index.html at the project root. Rename your entry page to index.html (or pass --dir <path>).` | Plain-HTML static publish, but the entry page isn't named `index.html` at the root | Rename the homepage to exactly `index.html` at the root, or pass `--dir <path>`. The CLI never guesses the entry. |
| `pull failed (HTTP <status>): <server message>` | No previous version exists yet (v1), **or** a legacy row with no stored source snapshot | Read the relayed server message. For a v1 changelog, skip the diff and write `"Initial version."`. For a legacy row with no source, ask the user for a manual `--message`. |
| ``No live versions to open yet. Run `artor publish` first.`` | `artor open` with nothing published | Publish first (`artor publish`), then `artor open`. |
| `Already linked to "<name>" (<id>) — pass --force to re-point.` | `artor link` on a dir that's already linked to a different project | If re-pointing is intended, re-run with `--force`. Otherwise you're in the wrong dir — check `artor status`. |
| `Already linked to project "<slug>".` (from `artor init`) | `init` in an already-linked dir | Not an error — `init` just re-runs registry login + skill sync. Publish directly. |
| Suddenly logged out after `artor dev` (on or off) | `artor dev` drops the stored token **and** default org on **every** switch (on or off) | `artor login` again (and re-select the org if you have 2+). `artor dev off` returns to production. |
| Preview shows "This version crashed while starting" / "needs more memory" (dashboard badge: **Failed to start**) after a publish that built fine locally | The version's server start failed — usually environment-dependent: a missing env var, a resource that only exists on your machine, or startup memory over the org plan's cap | `artor logs --json` retrieves the crash tail (the actual stack trace, plus `cause: "boot"` or `"oom"`). Fix the cause and re-publish — a new version starts immediately. See "Debugging a crashed version" in SKILL.md. |
| Publishing/reading against the wrong org | Wrong active/default org | `artor status`/`artor whoami` (or their `--json` `activeOrg`/`role`) name the org commands actually target; `artor org list` then `artor org use <ref>` to change the saved default, or pass `--org <ref>` on the one command. |
| `artor whoami` shows a different org than `artor status` used to imply | Not a contradiction: the **home** org (identity, from the token) differs from the **active** org (linked folder → saved default → home). `homeOrgMismatch: true` in `--json` | Nothing to fix. Report the **active** org as the target. Re-point the folder with `artor link --org <ref> <project> --force`, or change the default with `artor org use <ref>`, if the active org is wrong. |
| The active-org row reads "couldn't verify (the org listing didn't answer)" (`orgsUnavailable: true`) | The identity call succeeded but the membership **listing** failed (offline, server error) - the membership is **unknown**, not missing | Retry when the network/server is back. Do **not** tell the user they lost a membership, and do not suggest `artor link`. |
| `✗ "design" matches 2 projects - be more specific:` followed by candidates | An ambiguous partial ref. The CLI never guesses which one you meant, at any tier | Re-run with the **id** or the full slug/name from the listed candidates. Retrying the same ref will never resolve. |
| `✗ "demo" only matches project demo-archive partially. Unattended runs (--yes, or no terminal) must name it exactly` | A destructive command (`rm`, `folder rm`/`clear`, `space rm`/`read`/`members add\|rm`, `skill rm`, `skill pin --yes`, `share off`, `pull --project --force`) got a **partial** ref with no terminal to confirm against. `--org` on those runs is held to the same rule | Re-run naming the target **exactly** as the message says (it quotes the value to pass - the item's **id** when the name carries characters that can't be typed back). Never widen the ref to force a match. |
| A destructive command exited `1` printing `✗ Cancelled.` | The confirm was **declined** - this is a refusal, not a failure | Nothing broke and nothing was destroyed. Don't retry blind; re-ask the user, and add `-y`/`--yes` only once they've confirmed. |
| `✗ Cannot ask "…" without an interactive terminal. Re-run with --yes to confirm.` | A confirm was needed but nothing could ask or read the answer | Re-run with `--yes` once the user has confirmed. It is never a silent yes. |
| `✗ unknown command "pubish"` + `Did you mean "artor publish"?` | Typo. The suggester is conservative and deliberately **never** points at `artor rm` (two characters must be typed exactly) | Run the suggested command. If nothing is suggested, check `artor help` or `artor help <command>` - `-h`/`--help` works on every command, anywhere in the arguments, and never acts (`artor publish --help` does not publish). |
| `artor usage` returns 403 | Not an owner/admin of the resolved org (a non-member gets the same 403 - no membership oracle) | Ask an org owner/admin to read it, or check you're targeting the right org (`--org <ref>`, `artor status`). |
| `artor status` shows `corrupt (<reason>)` for the project | The local `.artor/project.json` link is malformed | Re-link: `artor link <slug>` (add `--force` if needed) to rewrite it, or `artor init` for a new project. |
| `No local (pullable) env vars at this scope. Nothing to write.` (from `artor env pull`) | The resolved scope (project + org, or org-only if unlinked) has no `local (pullable)` env vars | Nothing to fix. Server-only vars are never pulled; if a var should be downloadable, set it with `artor env set KEY=VALUE --local` (add `--scope org` for the org scope). |
| `Not in a linked project. Run inside one, or pass --org for the org scope.` (from `artor env`/`artor mock` `set`/`rm`) | A mutating `env`/`mock` verb run outside a linked project with no org scope - the CLI never silently targets the org from an unlinked dir | `cd` into the linked project, or pass `--scope org` explicitly if you meant the org-wide scope. |
| A one-line stderr note that `--org` is deprecated (from `artor env`/`artor mock`) | `--org` still works as a **scope** alias but has been superseded by `--scope org`, because `--org <ref>` names a target **organization** everywhere else in the CLI | Rewrite the command with `--scope org`. To change organization, run `artor org use` - `env`/`mock` always act on the current folder's org. |
| `env list --org acme` (or any `--org` a sub-command has no place for) is a hard error explaining both meanings | Ambiguity guard: the CLI refuses rather than quietly reading another org, or dropping the flag | Use `--scope org` for the scope; use `artor org use` to change organization. `--org` alongside a sub-command's own argument (`env set --org KEY=VALUE`, `mock rm --org users`) still works. |
| `env`/`mock set`/`list`/`rm` unexpectedly touched (or read) the whole org instead of one prototype | Old habit from before the default-scope change - inside a linked folder, `env`/`mock` default to the **project**, not the org | Pass `--scope org` explicitly when you actually want the org-wide scope; the project default is intentional (see "Behavior change" in SKILL.md). |
| ``mock revisions works at org or project scope only; --version is not supported`` | `artor mock revisions <name> --version <ref>` - a version pins exactly one sha, it has no separate history | Drop `--version`; run `artor mock revisions <name>` (project scope) or `--scope org` to see the history, then `artor mock pin <name> <sha> --version <ref>` to repoint the version. |
| Publish stops asking for `--mocks=local` or `--mocks=server` | The mock drift gate found `./mocks/*.json` files that differ from the linked project's server-effective mocks, and stdin isn't a TTY (or `CI`) so it can't prompt per-conflict | Pass `--mocks=local` to keep your local files, or `--mocks=server` to publish the server's current version instead. On a TTY, re-run without the flag to be prompted per conflict. |
| `artor publish --version <name>` warns on stderr that `--version` is deprecated | It still sets the **alias**, but the same spelling means a version NUMBER on `artor open` and the CLI's own version at `-V` | Use `--alias <name>` (short `-v`). If both are passed, `--alias` wins and the warning says so. |
| `artor env set KEY --stdin` refuses, printing the pipe form | It was run against a **terminal** - typing the secret there would echo it on screen and into scrollback | Pipe the value: `printf %s "$SECRET" \| artor env set KEY --stdin`. Also refused: `KEY=VALUE` together with `--stdin` (one value would be discarded), and an empty stdin read. |
| Private-package install fails (401/403 / missing scope) | Missing/stale `.npmrc` proxy block | `artor registry login` re-writes the managed `.npmrc` block (or re-run `artor pull`/`init`, which re-derive it). See `references/org-admin.md`. |
