# Troubleshooting

Symptom → cause → fix. Error strings below are the CLI's exact output; match against them, then apply
the fix. When the message is relayed from the server (e.g. `pull failed (HTTP …)`), read the relayed
text rather than expecting fixed CLI wording.

| Symptom (what you see) | Cause | Fix |
| --- | --- | --- |
| `command not found: artor` (or similar) | CLI not installed | Check `node --version` first: the CLI needs **Node 22 or newer** (`command not found: npm`/`node` means Node itself is missing; install the current LTS from https://nodejs.org, `brew install node` on macOS, or a version manager such as nvm, asking the user first). Then install the CLI — it publishes to npm as **`artor-cli`** (command stays `artor`): `npm install -g artor-cli` (or `pnpm add -g artor-cli`). Re-run `artor --version`. |
| `This account is suspended. Contact your organization admin or support.` | The token is valid but its account is suspended (artor-cli 0.28.0+; older CLIs print the generic `Token invalid or revoked` line) | **Stop.** Tell the user their account is suspended and to contact their organization admin or Artor support. Do **not** run `artor login` or retry in a loop: signing in again cannot lift a suspension (the web sign-in shows the same dead end). |
| ``This account is scheduled for deletion on <Month D, YYYY>. Run `artor login` and sign in with your password to restore it.`` (or ``This account is pending deletion. ...`` once that date has passed) | The account is pending deletion and not purged yet (artor-cli 0.28.0+) | Tell the user to run `artor login` and sign in with their **password**, then choose **Cancel deletion & sign in**. Magic-link and social sign-in cannot restore it; an account without a password needs the emailed cancel link or Artor support. Only they can do this; you cannot cancel the deletion for them. Once restored, the existing CLI token works again, so retry the original command. |
| ``Token invalid or revoked. Run `artor login`.`` | The token was revoked, expired, or its account no longer exists (also every blocked-account case on CLIs before 0.28.0) | Ask the user to run `artor login`, then retry. If login then reports a suspended account, stop and tell them to contact their admin or support. |
| ``Several of your accounts could act here. Pass --account <email> (see `artor account list`).`` | Two or more stored accounts are members of the org this command would target (the folder's org, or the org an `--org` ref resolved to) | Show the user the accounts that hold that org and ask which to act as, then re-run with that `--account <email>`. Never guess - each account can act very differently in the same org. |
| `This folder isn't linked and more than one org could be meant. Pass --org <slug> (and --account <email> if more than one account is a member).` | An unlinked folder, a command that needs an org, and more than one (account, org) pair is possible | Ask the user which org (and, if the message says so, which account) they mean, then re-run with `--org <slug>` (and `--account <email>` if needed). Never guess. |
| ``No logged-in account "<value>" on this server. Run `artor account list`, or `artor login` to add it.`` | `--account` didn't match any stored login's email or user id exactly (it never does partial matching) | Run `artor account list` for the exact email, or `artor login` to add the missing account. Retype the email exactly - a typo or a substring never matches. |
| ``This folder belongs to an org none of your logged-in accounts is in. Run `artor login` with an account that is, or `artor account list` to see what's stored.`` | The folder's linked org isn't held by any stored account | Ask the user which account is a member (or check the dashboard), then `artor login` as it. Don't retry the same command - no stored account will make it work. |
| ``This folder is linked to <org>, but --org names <other>. To move it, run `artor unlink --link-only` then `artor link <project> --org <other>`. Or drop --org to use <org>.`` | `--org` names an org that differs from the one this folder is already linked to | Either drop `--org` (act in the folder's real org), or deliberately re-point the folder: `artor unlink --link-only` then `artor link <project> --org <other>`. Never silently follow the mismatched `--org` and never silently ignore it - relay the refusal. |
| ``This folder is linked to <org>, but --org names <other>, which matches several orgs (<a>, <b>). To move it, run `artor unlink --link-only` then `artor link <project> --org <slug>` with the exact slug. Or drop --org to use <org>.`` | Same conflict, but the `--org` ref you passed was itself ambiguous (matched several orgs, none of them the folder's) | Ask the user for the exact target org slug before suggesting `link`; a ref that was already ambiguous can't be reused as the `--org` value on the re-link command. |
| ``This folder is linked to <org>, so a new project can't be created inside it for <other>. Run artor init from a folder outside it, run `artor unlink --link-only` first to detach this folder, or drop --org to create it in <org>.`` | `artor init --org <other>` run inside a folder already linked to a different org | `init` never re-links an existing folder to a new project. Run it from a folder outside the linked one, unlink first (`artor unlink --link-only`), or drop `--org` to create the new project in the folder's existing org. |
| ``This folder is linked to <org>, but --org names <other>. Run the command from a folder that isn't linked to <org>, or drop --org to use <org>.`` | `artor remix` or `artor pull --project <ref> --dir <p>`: these write into ANOTHER folder, so re-linking THIS folder (the usual D-a advice) would be the wrong fix | Run the command from a folder that isn't linked to `<org>`, or drop `--org` to act in `<org>`. |
| ``\`artor env\` acts in the linked folder's org, and this folder isn't linked. Run it in a folder linked to the org you mean, or in an interactive terminal to pick the org.`` (also `artor mock`) | `env`/`mock`'s `--org` means the org SCOPE, not a target, so an unlinked folder with several possible orgs and no terminal to pick has no `--org` escape hatch here | Ask the user which org they mean, then `cd` into a folder linked to it. Never pass `--org` to fix this - it means the org scope for `env`/`mock`, not a target org. |
| ``Your org list changed: --org "<ref>" no longer names the org this command checked. Nothing was changed. Run `artor account list` to refresh your orgs, then run it again.`` | The org `--org` named dropped off the live list between the check and the write - a stale membership cache, a removal, or a rename raced the command (`init`/`link`) | Nothing was changed - safe to retry. Run `artor account list` to refresh, confirm the org with the user, then run the original command again. |
| ``Your org list changed: the org this command checked is no longer one of your orgs. Nothing was changed. Run `artor account list` to refresh your orgs, then run it again.`` | Same race, but with no `--org` at all: the org `artor init`/`artor link` resolved on its own (a picker answer, or the unlinked single-org shortcut) dropped off the live list before the write | Nothing was changed - safe to retry. Run `artor account list` to refresh, confirm the org with the user, then run the original command again. |
| ``No logged-in account "<value>". Run `artor account list`.`` (from `artor logout --account`) | `--account` on `artor logout` didn't match any stored login's email or user id exactly | Exit 1, nothing was revoked. Run `artor account list` for the exact email, then retry `artor logout --account <email>`. |
| ``--account "<email>" matches N logged-in accounts with that email (user ids ...). Pass --account <user id> instead (`artor account list --json` shows them).`` | Two or more stored accounts share the same email (rare, but not impossible: separate identities can register with the same address) | Ask the user which account (by user id) they mean, then re-run with `--account <user id>` - `artor account list --json` lists the candidates' user ids. |
| ``\`artor <cmd>\` does not take --account.`` | `--account` was passed to a command that never resolves a single account: `artor account list`, `dev`, `update`, `update-skill`, `install*`, or `unlink` | Drop `--account` - none of these commands can use it. |
| ``This CLI is too old for the Artor server. Run `artor update`.`` (HTTP 426) | Server's minimum-CLI floor was bumped, and the CLI's automatic self-heal (0.16.0+: update + re-run the command once) wasn't possible here (CI, `npx`/project-local install, auto-update off, or the update failed) | `artor update`, then retry the command. |
| `This server does not support the current publish protocol. The server is older than this CLI; ask your Artor operator to update it.` | The **server** predates the streaming publish protocol (the reverse of the 426 case) | Nothing on the CLI side fixes this — the self-hosted Artor server needs updating. Tell the user to contact their operator. |
| ``boot smoke test failed: the bundle crashes on `node <entry>` before binding its port: …`` (ends: ``Fix the build, or re-run with `--no-smoke` if your app legitimately needs runtime env/services to boot.``) | The built bundle crashes on startup (e.g. missing dependency, bad import) | Read the crash output and **fix the build**. Only re-run with `--no-smoke` if the app **legitimately** needs live secrets/services to boot — never as a reflex to bypass a genuine crash. |
| `couldn't detect a framework, a build script, or an index.html. Pass --dir <build-output>, or --node --entry <server.js> for a server.` | Running `publish` where there's no detectable app — usually a **monorepo/workspace root** | `cd` into the specific app's folder (the one whose `package.json` has the `build` script + framework dep) and publish there. Or pass `--dir`/`--node --entry` if the output/entry is non-standard. |
| ``no `build` script in package.json. Pass --dir <build-output> instead.`` | Same as above — cwd has a `package.json` but no `build` script | `cd` into the real app folder, or pass `--dir <build-output>`. |
| ``.next/standalone exists but has no server.js. Checked …`` / ``found more than one Next server in .next/standalone: …`` / ``… the search was cut short …`` | A Next app in a monorepo whose standalone server publish could not locate unambiguously (artor-cli 0.34.0+ looks at the root `server.js`, the path implied by `outputFileTracingRoot` or the workspace root, then a bounded search) | Set `outputFileTracingRoot` in `next.config` to the workspace root and re-publish. Or publish the server by hand: copy `.next/static` and `public` next to that `server.js`, then `artor publish --node --dir .next/standalone --entry <path/to/server.js>`. |
| ``this app's dependencies are not installed and --no-install was set. Run `<pm> install` in the workspace root "<path>" first, then re-publish.`` | `--no-install` in a workspace app whose dependencies are missing (artor-cli 0.34.0+ installs at the workspace root on its own when the flag is absent) | Run the named install in the workspace root, or drop `--no-install` and re-publish. |
| `npm install` fails on `workspace:*` (`EUNSUPPORTEDPROTOCOL`) during a monorepo publish, or publish looks only for `.next/standalone/server.js` | A CLI older than 0.34.0 (it detected the package manager from the app folder and fell back to npm) | `artor update`, then re-publish from the app folder. |
| `found .html files but no index.html at the project root. Rename your entry page to index.html (or pass --dir <path>).` | Plain-HTML static publish, but the entry page isn't named `index.html` at the root | Rename the homepage to exactly `index.html` at the root, or pass `--dir <path>`. The CLI never guesses the entry. |
| `pull failed (HTTP <status>): <server message>` | No previous version exists yet (v1), **or** a legacy row with no stored source snapshot | Read the relayed server message. For a v1 changelog, skip the diff and write `"Initial version."`. For a legacy row with no source, ask the user for a manual `--message`. |
| ``No live versions to open yet. Run `artor publish` first.`` | `artor open` with nothing published | Publish first (`artor publish`), then `artor open`. |
| `This server does not support --signed-in yet, or the prototype is not visible to you.` | `artor open --signed-in` against a server that predates signed-in links, **or** a prototype in a space you can't see | Check you're in the right org/project (`artor status`). If so, the server is older: ask the user to open plain `artor open --json`'s `url` in their own signed-in browser. |
| `--<flag> needs a value.` (exit 1) | A value flag followed by another `--flag` or by nothing (artor-cli 0.27.0+; a few flags such as `--org` and `-m` word it their own way) | Supply the value. A free-text value that really starts with `--` uses the `=` form: `--message=--hotfix`. |
| `Already linked to "<name>" (<id>) - pass --force to re-point.` | `artor link` on a dir that's already linked to a different project | If re-pointing is intended, re-run with `--force` (`--force` re-points within the same org only; to move it to another org, run `artor unlink --link-only` first). Otherwise you're in the wrong dir - check `artor status`. |
| `Already linked to project "<slug>".` (from `artor init`) | `init` in an already-linked dir | Not an error — `init` just re-runs registry login + skill sync. Publish directly. |
| `artor dev` shows no login | You have no login on that server yet - logins and default orgs are stored **per server**, so a fresh `artor dev` target starts with none | `artor login` on that target. `artor dev off` returns to production, where your prior logins are exactly as left. |
| Preview shows "This version crashed while starting" / "needs more memory" (dashboard badge: **Failed to start**) after a publish that built fine locally | The version's server start failed — usually environment-dependent: a missing env var, a resource that only exists on your machine, or startup memory over the org plan's cap | `artor logs --json` retrieves the crash tail (the actual stack trace, plus `cause: "boot"` or `"oom"`). Fix the cause and re-publish — a new version starts immediately. See "Debugging a crashed version" in SKILL.md. |
| Publishing/reading against the wrong org | Wrong active/default org, or the wrong stored account resolved for it | `artor status`/`artor whoami` (or their `--json` `activeOrg`/`role`/`account`) name the org and account commands actually target; `artor org list` then `artor org use <ref>` to change the picker's pre-selection, or ask the user which org (and account) they mean and re-run with `--org <ref>` (and the `--account <email>` the user names) on the one command. |
| A command in a linked folder acted as the wrong stored account (or you're not sure which one acted) | Several stored accounts are members of that folder's org | Read the `-> org · email · …` line on stderr, or `status --json`'s `account` field, before trusting who acted. `artor account list` shows which accounts hold that org; ask the user which one, then re-run with the `--account <email>` the user names. |
| `artor account list` shows a row with `- token now signs in as a different account: run artor login and sign in as <email>` | The stored token for that email now answers as a **different** user (server-side identity changed under it) | Run `artor login`, sign in as that exact email in the browser, and it refreshes in place. |
| `artor account list` shows a row with `- token no longer valid: run artor login and sign in as <email>` | That account's token is dead (revoked, expired) | Run `artor login`, sign in as that exact email. |
| `artor account list` row says `- couldn't check (server unreachable)` or `- couldn't check (HTTP <n>)` | The live token re-check timed out or the server errored - not a verdict on the token itself | Retry later. Don't tell the user the account is broken; nothing was actually confirmed either way. |
| ``artor account list`` prints ``N login(s) not identified yet: the server couldn't be reached to check <it/them>. <It is/They are> identified automatically once the server answers; run `artor account list` again then.`` | A login this machine hasn't identified yet (an older CLI's token, or one just approved) couldn't reach the server this run (`--json` pending row `reason: "unreachable"`) | Nothing to fix - re-run `artor account list` later; it identifies itself automatically once the server answers. |
| ``artor account list`` prints `N login(s) not identified yet: <account-state sentence>` (e.g. `This account is suspended. Contact your organization admin or support.`) | A not-yet-identified login's account IS the one blocked (`--json` `reason: "suspended"` or `"deletion_pending"`) | Relay the account-state sentence exactly as for an identified account's row - contact an admin/support, or sign in with a password and choose Cancel deletion & sign in. |
| ``artor account list`` prints ``N login(s) not identified yet: the server answered HTTP <status>. Run `artor account list` again later.`` | A not-yet-identified login's check failed for another reason (`--json` `reason: "error"`, `httpStatus`) | Re-run `artor account list` later. Not a verdict on the token. |
| ``artor account list`` prints ``1 login not identified yet: the server recognized it, but saving that failed (another artor command may be holding the account store). Run `artor account list` again.`` | The server confirmed the login, but writing it to the local account store failed, usually because another `artor` command held the store's lock at the same moment (`--json` `reason: "unsaved"`) | Nothing wrong with the login itself. Just re-run `artor account list`. |
| `artor account list` prints `N login(s) not identified yet.` with no further detail | The login simply wasn't checked this run (`--json` pending row has no `reason`) | Re-run `artor account list` to check it. |
| ``<email> is not a member of this folder's org. Run `artor account list`.`` | An explicit `--account <email>` names a real, stored account, but it isn't a member of the folder's linked org | Ask the user which account should be used, or `artor login` with an account that is a member. Don't retry with the same `--account`. |
| ``This machine's login hasn't been identified yet, so --account can't match it. Run `artor account list` (it identifies it), then retry.`` | `--account` was passed while the only login on this server is one an older CLI made and this CLI has not identified yet (nothing has actually been matched or rejected) | Run `artor account list` once (it identifies pending logins), then retry the original command with `--account <email>`. |
| `Several accounts are logged in. Pass --account <email>, or --all.` (from `artor logout`) | `artor logout` with 2+ stored accounts and no `--account`/`--all`, and no terminal to pick interactively | Ask the user which account (or all) to log out, then re-run `artor logout --account <email>` or `--all`. |
| `Couldn't revoke on the server; revoke it in Settings > CLI tokens.` (from `artor logout`) | The token was removed/replaced locally, but the server-side revoke call failed (network, transient error) | The account is signed out locally either way, but the old token may still be **live** on the server. Tell the user to revoke it manually in Settings > CLI tokens. |
| `Couldn't revoke the previous token on the server; revoke it in Settings > CLI tokens.` (from `artor login`) | Logging in again as an account already held refreshed its token locally, but revoking the DISPLACED previous token on the server failed | The new login works either way, but the old (displaced) token may still be **live** on the server. Tell the user to revoke it manually in Settings > CLI tokens. |
| `artor whoami` shows a different org than `artor status` used to imply | Not a contradiction: the **home** org (identity, from the account) differs from the **active** org (`--org` → linked folder → unlinked resolution). `homeOrgMismatch: true` in `--json` | Nothing to fix. Report the **active** org as the target. Re-point the folder with `artor unlink --link-only` then `artor link <project> --org <slug>`, or change the picker's pre-selection with `artor org use <ref>`, if the active org is wrong. |
| The active-org row reads "couldn't verify (the org listing didn't answer)" (`orgsUnavailable: true`) | The identity call succeeded but the membership **listing** failed (offline, server error) - the membership is **unknown**, not missing | Retry when the network/server is back. Do **not** tell the user they lost a membership, and do not suggest `artor link`. |
| `` `artor status` shows `Couldn't check which of your accounts is in this folder's org: the saved org list may be out of date, and refreshing it failed. Run `artor account list` to check your accounts.` `` (`--json` `orgsStale: true`) | `status` tried one bounded refresh of the account's org list (the only reason nothing matched) and that refresh itself failed (offline, a dead token, a busy lock) - it is **unknown** whether the account is a member, not confirmed no | Re-run the command (or `artor account list`) once conditions improve. Never tell the user they are not a member - that is `accountMismatch`, a different, confirmed state. With `--org <ref>`, the same sentence says "in an org matching \"<ref>\"" instead. |
| `Not a member of org "<orgId>" (or it no longer exists). Run "artor org list" to see your orgs. To move this folder to another org, run "artor unlink --link-only" then "artor link <project> --org <slug>". Outside a linked folder, pass "--org <slug>".` (from `artor whoami`/`artor status`) | The org the command sent (`X-Artor-Org`) returned a 403: a stale/hand-edited `.artor`, a left-behind clone, or a revoked membership | Relay all three remedies as written: list orgs, re-point a linked folder (`unlink --link-only` then `link --org`), or pass `--org` outside a linked folder. |
| `✗ "design" matches 2 projects - be more specific:` followed by candidates | An ambiguous partial ref. The CLI never guesses which one you meant, at any tier | Re-run with the **id** or the full slug/name from the listed candidates. Retrying the same ref will never resolve. |
| `✗ "demo" only matches project demo-archive partially. Unattended runs (--yes, or no terminal) must name it exactly` | A destructive command (`rm`, `folder rm`/`clear`, `space rm`/`read`/`members add\|rm`, `skill rm`, `skill pin --yes`, `share off`, `pull --project --force`) got a **partial** ref with no terminal to confirm against. `--org` on those runs is held to the same rule | Re-run naming the target **exactly** as the message says (it quotes the value to pass - the item's **id** when the name carries characters that can't be typed back). Never widen the ref to force a match. |
| A destructive command exited `1` printing `✗ Cancelled.` | The confirm was **declined** - this is a refusal, not a failure | Nothing broke and nothing was destroyed. Don't retry blind; re-ask the user, and add `-y`/`--yes` only once they've confirmed. |
| `✗ Cannot ask "…" without an interactive terminal. Re-run with --yes to confirm.` | A confirm was needed but nothing could ask or read the answer | Re-run with `--yes` once the user has confirmed. It is never a silent yes. |
| `✗ unknown command "pubish"` + `Did you mean "artor publish"?` | Typo. The suggester is conservative and deliberately **never** points at `artor rm` (two characters must be typed exactly) | Run the suggested command. If nothing is suggested, check `artor help` or `artor help <command>` - `-h`/`--help` works on every command, anywhere in the arguments, and never acts (`artor publish --help` does not publish). |
| `artor usage` returns 403 | Not an owner/admin of the resolved org (a non-member gets the same 403 - no membership oracle) | Ask an org owner/admin to read it, or check you're targeting the right org (`--org <ref>`, `artor status`). |
| `artor status` shows `corrupt (<reason>)` for the project | The local `.artor/project.json` link is malformed | Re-link: `artor link <slug>` (add `--force` if needed) to rewrite it, or `artor init` for a new project. |
| `No local (pullable) env vars at this scope. Nothing to write.` (from `artor env pull`) | The resolved scope (project + org, or org-only if unlinked) has no `local (pullable)` env vars | Nothing to fix. Server-only vars are never pulled; if a var should be downloadable, set it with `artor env set KEY=VALUE --local` (add `--scope org` for the org scope). |
| `Not in a linked project. Run inside one, or pass --org for the org scope.` (from `artor env`/`artor mock` `set`/`rm`) | A mutating `env`/`mock` verb run outside a linked project with no org scope - the CLI never silently targets the org from an unlinked dir | `cd` into the linked project, or pass `--scope org` explicitly if you meant the org-wide scope. |
| A one-line stderr note that `--org` is deprecated (from `artor env`/`artor mock`) | `--org` still works as a **scope** alias but has been superseded by `--scope org`, because `--org <ref>` names a target **organization** everywhere else in the CLI | Rewrite the command with `--scope org`. `env`/`mock` act on the linked folder's org; to use another org, run from a folder linked to it (or re-link with `artor unlink --link-only` + `artor link <project> --org <slug>`). |
| `env list --org acme` (or any `--org` a sub-command has no place for) is a hard error explaining both meanings | Ambiguity guard: the CLI refuses rather than quietly reading another org, or dropping the flag | Use `--scope org` for the scope. `env`/`mock` act on the linked folder's org; to use another org, run from a folder linked to it (or re-link with `artor unlink --link-only` + `artor link <project> --org <slug>`). `--org` alongside a sub-command's own argument (`env set --org KEY=VALUE`, `mock rm --org users`) still works. |
| `env`/`mock set`/`list`/`rm` unexpectedly touched (or read) the whole org instead of one prototype | Old habit from before the default-scope change - inside a linked folder, `env`/`mock` default to the **project**, not the org | Pass `--scope org` explicitly when you actually want the org-wide scope; the project default is intentional (see "Behavior change" in SKILL.md). |
| ``mock revisions works at org or project scope only; --version is not supported`` | `artor mock revisions <name> --version <ref>` - a version pins exactly one sha, it has no separate history | Drop `--version`; run `artor mock revisions <name>` (project scope) or `--scope org` to see the history, then `artor mock pin <name> <sha> --version <ref>` to repoint the version. |
| Publish stops asking for `--mocks=local` or `--mocks=server` | The mock drift gate found `./mocks/*.json` files that differ from the linked project's server-effective mocks, and stdin isn't a TTY (or `CI`) so it can't prompt per-conflict | Pass `--mocks=local` to keep your local files, or `--mocks=server` to publish the server's current version instead. On a TTY, re-run without the flag to be prompted per conflict. |
| `artor publish --version <name>` warns on stderr that `--version` is deprecated | It still sets the **alias**, but the same spelling means a version NUMBER on `artor open` and the CLI's own version at `-V` | Use `--alias <name>` (short `-v`). If both are passed, `--alias` wins and the warning says so. |
| `artor env set KEY --stdin` refuses, printing the pipe form | It was run against a **terminal** - typing the secret there would echo it on screen and into scrollback | Pipe the value: `printf %s "$SECRET" \| artor env set KEY --stdin`. Also refused: `KEY=VALUE` together with `--stdin` (one value would be discarded), and an empty stdin read. |
| ``This organization requires a password on public links. Re-run with --password (or --password-stdin in scripts).`` (403 `share_password_required`) | The organization requires a password on every public link, and this unattended `artor share add` sent none | Get a password from the user (or generate one and show it once), then retry: `printf '%s' "$PW" \| artor share add --password-stdin`. On an interactive terminal the CLI asks in place instead of failing. |
| `This organization requires a password on public links, so it can't be removed.` | `artor share set <share> --remove-password` while the org requirement is on | Leave the password on, or ask an org admin to turn the requirement off first. Setting a **different** password still works. |
| `--password takes no value (it prompts). Pipe it with --password-stdin instead.` (or `--password-stdin takes no value…`, `--remove-password takes no value.`) | A password was passed as a flag VALUE (`--password=x`, `--password x`).
